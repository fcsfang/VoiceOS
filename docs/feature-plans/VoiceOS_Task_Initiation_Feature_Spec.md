# VoiceOS「任务启动」功能需求与实现规格（V1）

> 文档定位：交付给现有 VoiceOS 仓库中的开发 Agent 的**产品需求 + 行为规格 + 验收依据**。  
> 版本：1.0（2026-11-10）  
> 优先级：在不推翻 VoiceOS 既有语音、双模式、知识及行动系统的前提下，完成可工作的最小闭环。  
> 配套文档：《VoiceOS_Implementation_Agent_Prompt.md》。

## 0. 一页摘要

### 产品定义

VoiceOS 是用户与 AI 的**持续语音交互入口及任务启动层（Task Initiation Layer）**，不是 Codex / Claude Code 的替代品。用户以自然语言说出一个不完整的目标、困难或想法，VoiceOS 负责理解、适度澄清、结合已授权上下文，将它转化成一个**可以立即开始的下一步**。

可能的产物包括：

1. **交给专业 Agent 的可复制任务提示词 / 交接包**；
2. **用户自己执行的最小可操作教程**；
3. **在尚未明确目标时帮助用户厘清问题**；
4. **仅记录、暂缓行动**；
5. **针对已存在任务，找回上下文并生成下一步启动材料**（在现有系统已支持任务状态时纳入首版，否则增量完成）。

一句话原则：**人表达意图，VoiceOS 把意图转化为行动入口，专业工具负责执行，用户把关重要决策。**

### 首版必须做到

用户说「老师让我做一份 PPT，我不会，也不知道怎么开始」—— VoiceOS 应能：
- 识别这是一个潜在的“需要启动任务”的表达，而不是单纯知识问答；
- 在必要时询问最关键的一个问题，或以显式假设先给出初稿；
- 推荐“交给制作 Agent / 获取操作教程 / 先梳理思路”等恰当路线，并尊重用户选择；
- 输出实用的、可复制和编辑的任务提示词，或真正能动手的操作步骤；
- **不能**未经确认直接创建外部任务、发送资料、调用外部执行 Agent 或将私人内容写入长期记忆；
- 能让用户在后续会话中找到该任务的已确认状态（优先复用现有任务系统）。

### 非目标

本功能**不**重造 Codex、Claude Code、文档/PPT/视频编辑器，不承担多工具自主执行编排，不以「万物自动建待办」为目标，不进行大范围架构重写。

## 1. 背景、用户问题和成功定义

### 1.1 用户问题

- 接到陌生任务时，常因「不知道从哪里开始」而拖延。
- 用户明明能用专业 Agent/工具完成任务，却难以把模糊想法变成清晰的请求。
- 每次切换工具都要重新交代背景、需求、限制与验收方式。
- 过度委托可能完成交付却无法获得必要的理解与成长。
- 纯记录系统容易积累大量想法，但不能有效帮助开始行动。

### 1.2 核心价值

将「模糊的意图」低摩擦转化为「明确的起步动作」，降低心理和认知启动成本。这里的“启动”既包括新任务开始，也包括搁置任务恢复、卡住任务重新明确下一步。

### 1.3 成功标志（不是虚构的性能承诺）

- 用户能从一段口述，在同一会话中得到**可立即使用**的启动产物；
- 输出不是空泛鼓励，而是包含目标、当前上下文、约束、交付要求和验证方式的具体内容；
- 用户能够辨别哪些来自自己，哪些是系统假设或建议；
- 安静记录模式不被主动追问打断；
- 不出现未经同意的外部执行、发送或持久化；
- 首版与原有语音输入/对话/知识/待办功能兼容。

## 2. 角色边界与协作协议

| 角色 | 负责 | 不负责 |
|---|---|---|
| 用户 | 表达意图；选择委托、学习或记录；重要审批与验收 | 提前组织完美的提示词 |
| VoiceOS | 理解/澄清、推荐路线、整理任务、生成交接包或步骤、可控记录与恢复 | 替专业 Agent 实现代码、制作视频、在无人确认时跨系统执行 |
| 专业 Agent / 工具 | 在自身环境中完成具体工作；提供可核实结果 | 代替用户定义真实目标与最终责任 |

**边界规则：** VoiceOS 可以建议执行者（例如 Codex、Claude Code 或适当的专业工具），但 V1 默认只生成交接材料供用户自行复制/转交；不因生成了提示词而宣称已完成目标任务。

## 3. 统一功能模型：一次表达 → 四种启动路线

不做多个互不相关的「提示词工具 / 教程工具 / 创意工具」。在现有语音与文本交互中接入统一的任务启动能力。

### 路线 A：Agent 交接（`agent_handoff`）

**触发示例**：「我想让 Codex 开发这个功能，但不知道怎么说。」「帮我整理一份能让 Agent 开始工作的提示词。」

**输出**：一份可复制、可编辑的任务提示词；必要时带上简短交接信息（目标、参考上下文、约束、交付物、验收标准、需要 Agent 在环境中查证的未知项）。

要求：
- 不假装已经读取代码、文件、日程或外部服务；缺少资料时让执行 Agent 先检查真实环境。
- 不得把推测伪装为事实。例如“现有仓库应该有模块 X”应改成“请先定位对应模块”。
- 可指定执行偏好：`quick_delivery`（以交付为主）、`learn_while_doing`（交付且解释关键实现）。
- 内容要能交给新会话中的 Agent 单独理解，不能依赖 VoiceOS 的隐性上下文。

### 路线 B：自我操作教程（`guided_start`）

**触发示例**：「这个软件我不会用，告诉我第一步怎么操作。」「我想自己学会。」

**输出**：目标、开始前需要的条件、3–7 个可操作步骤、第一步的明确动作、如何验证做到，以及可能需要补充的信息。未知软件版本和操作环境要显式标注，不造菜单和按钮。

原则：先帮用户迈出第一步；避免一口气输出冗长教科书。

### 路线 C：共同澄清（`clarify`）

**触发示例**：「我有个想法但说不清楚。」「三个方案我不知道选哪个。」

**输出**：对目标与不确定性的简短复述，以及**一个最能影响下一步的澄清问题**，或提供带前提的初步选项；用户明确要求深入讨论时才展开多轮讨论。

### 路线 D：安静记录（`capture_only`）

**触发示例**：「我先记一下一个灵感，不用做。」「今天这件事真烦。」

**输出**：按既有规则记录或回应，不自动创建任务、不默认转换为提示词、不强制追问。对涉及长期个人认知的知识，沿用 VoiceOS 既有“暂定/候选”确认机制。

### 可选延伸：任务恢复（`resume_task`）

用户说「上周那个任务重新开始」，在可以可靠找到**同一个任务**且有已确认状态时，输出当前状态、未解决阻碍、建议的下一步，以及必要的新版提示词。找不到对应任务时不要编造进度，先请求识别。

## 4. 意图识别与触发规则

### 4.1 输入

- 复用 VoiceOS 已有语音转写与文本聊天链路；支持纯文本作为可测试入口。
- 可获取**已经授权**的短期对话上下文、任务记录、个人知识（需要可靠来源）。
- 允许从语音转写的口语、重复、犹豫中提取意图，不要求用户提供格式化命令。

### 4.2 判断维度

区分以下信号：
- **行动需求**：需要开始/继续/交付某项工作；
- **信息需求**：只想理解概念或得到回答；
- **情绪表达 / 自由思考**：不必安排任务；
- **明确否定**：「别安排」「只是吐槽」「先记录」。

以用户显式意图优先，隐含意图保守推断。**不能单靠出现「任务、难、不会」等关键词就自动执行或建任务。**

### 4.3 与双模式兼容

- **A 安静记录者（默认）**：允许内部提取「可能需要启动」的候选标记，但不打断口述、不主动多轮追问；按当前交互模式把建议留在整理后的内容中，需用户主动选择后才能生成/确认交接包。
- **B 对话式伙伴**：可在合适时机说「我可以先帮你生成交给 Codex 的任务说明，还是先带你做第一步？」；一次只问一个最关键问题，允许用户跳过并按假设出草稿。
- 用户明确说「生成提示词 / 教我 / 不要处理」时，明确指令优先于自动推断。

### 4.4 决策与不确定性

内部结构可包含 `intent`, `route`, `confidence`, `missing_key_information`, `reason`，但不要将 LLM 自报的置信度当成硬安全依据。对不确定的触发采用**不升级权限、不擅自创建待办**的默认行为。必要的澄清优先于武断生成。

## 5. 需求澄清与产物生成

### 5.1 最小信息清单

通常尝试获得：

1. **目标**：最终想改变什么、解决什么；
2. **期望交付物**：报告、代码、PPT、行动方案等；
3. **已知上下文**：目前状况、已有资料、已有进度；
4. **约束**：截止时间、平台、工具、权限、质量要求等（没有就标未知）；
5. **执行偏好**：让 Agent 做 / 自己跟着教程做 / 先讨论 / 先保存；
6. **成功标准**：怎样知道做成了。

不要求用户一次提供全部字段。只追问影响启动路线或关键安全决策的信息；其他部分可先输出**带明确假设的草稿**。

### 5.2 自动选择路线与用户控制

VoiceOS 可以推荐路线，但用户应能通过语音或现有 UI 改成另一条路线；不要自动锁死。默认优先采用最小干预、能取得实际进展的方式。

### 5.3 提示词质量要求

Agent 提示词的推荐结构：

```markdown
# 任务目标
[用户真正希望得到的结果]

# 已知背景
[经用户提供/获授权上下文确认的事实，必要时标注来源]

# 约束与偏好
[时间、环境、限制，以及更倾向快速交付还是边做边学]

# 请先做的事
[如果缺少仓库/文件/工具现状，请先检查，再制定实施步骤]

# 执行要求
[分步实现、遵守现有架构、必要时验证、明确假设]

# 预期交付物
[文件、报告、代码、结论等]

# 验收标准
[可检查的完成条件]

# 遇到阻碍时
[说明缺失信息与最小可继续方案，不得编造事实]
```

生成内容**必须可直接复制**，不能只有“建议你让 Codex 做这些事”的第三人称转述。对于指定 Codex/Claude 的情形，可调整措辞，但不要声称拥有该工具未验证的能力。

### 5.4 语音和视觉输出的不同粒度

- 语音回复宜短：总结理解、推荐路线、一个确认点、可立即采取的动作；
- 完整提示词/教程是可展开的文字产物，不通过语音一次性朗读长篇；
- 首版 UI 优先使用已有聊天/卡片/复制能力，**不为了此功能重做界面**。

## 6. Task Package（任务交接包）

这是**逻辑数据模型**，不是强制数据库 schema。Agent 必须先审计现有任务/记录/消息实体，再决定复用字段还是新增轻量结构。

### 6.1 建议字段

```json
{
  "schema_version": "1",
  "id": "system-generated-id",
  "title": "制作课程演示PPT",
  "origin": {
    "source": "voice_or_text",
    "conversation_ref": "optional-reference"
  },
  "objective": "制作能用于课程汇报的PPT",
  "route": "agent_handoff",
  "execution_preference": "quick_delivery",
  "target_executor": "user_selected_or_suggested_tool",
  "known_facts": ["老师要求制作一份PPT"],
  "assumptions": ["受众和时长尚未确定"],
  "missing_information": ["主题、听众、时长、提供的材料"],
  "constraints": [],
  "handoff_prompt": "...",
  "guide_steps": [],
  "acceptance_criteria": ["内容与指定主题相关", "结构清晰", "引用准确"],
  "status": "draft",
  "confirmed_by_user": false,
  "source_refs": [],
  "created_at": "system-timestamp",
  "updated_at": "system-timestamp"
}
```

**约束：** 示例仅用于表达意图；字段命名、存储、时区、ID、状态机制以仓库现有规范为准。不要把 `"..."` 当真实提示词持久化。个人知识不得因为生成交接包就自动晋升为已确认事实。

### 6.2 最小状态语义

- `draft`：AI 整理的候选产物，尚未确认；
- `confirmed`：用户认可该任务/交接内容；
- `exported`：用户已复制/导出交接材料（**不代表专业 Agent 已执行**）；
- `in_progress`、`blocked`、`completed`：有可靠来源的后续人工标记/既有任务状态。

避免以“复制成功 = 任务完成”混淆任务实际进度。若现有系统已有任务状态机，建立映射，不额外复制一套。

### 6.3 可追溯性

事实与推测分开；原始输入不必重复保存完整音频（遵循既有数据策略），但产物应能指回会话/授权资料。不可泄露密码、密钥、敏感公司信息。复制或交付包含私人/企业资料的提示词前，提供适度的提醒或显式确认（沿用现有权限与隐私机制）。

## 7. 用户旅程与场景脚本

### 场景 S1：陌生 PPT 任务 → Agent 交接

**用户**：「老师要我做 PPT，我不会做，想让 AI 帮忙。」  
**VoiceOS（B 模式）**：「可以先帮你准备给制作工具的任务说明。老师给了主题和材料吗？」  
**用户**：「主题是 X，材料在一个文件里。」  
**VoiceOS**：输出 PPT 任务交接包，明确材料文件需在专业工具中提供；未访问文件时不编造内容。包含听众与长度未确定的假设、建议结构和验收标准。  
**成功**：用户能复制提示词，知道还需要给 Agent 哪份材料。

### 场景 S2：Codex 开发 → 委托且学习

**用户**：「我需要让 Codex 完善 Skill Hub 的自动升级，帮我写提示词。我也想弄懂关键代码。」  
**VoiceOS**：输出 `agent_handoff`，`learn_while_doing`：要求 Codex 先扫描仓库，列出实现方案，再增量实现并测试，最后解释关键文件、入口、调用链和验证方法。  
**成功**：提示词能脱离 VoiceOS 单独交给执行 Agent，并含清晰验收项。

### 场景 S3：用户想自己学

**用户**：「我想自己学 Git Hook，不用让 Agent 代写。」  
**VoiceOS**：选择 `guided_start`，先给出最小实验（环境、操作、预期结果、失败排查），避免输出“请阅读官方文档”式空泛建议。  
**成功**：用户知道下一步要操作什么、怎样确认成功。

### 场景 S4：情绪表达不是任务

**用户**：「今天实习任务真烦，我只想吐槽一下。」  
**VoiceOS**：回应并遵守记录模式，不生成交接包、不创建待办、不追问「什么时候完成」。  
**成功**：不会误触发任务化。

### 场景 S5：自由口述，默认安静模式

**用户**：（连续几分钟口述研究灵感、工作困惑和日常感受。）  
**VoiceOS**：不在口述中插话；结束后按既有系统整理，允许出现一个可选建议「其中 A 看起来可以转成启动任务」，但不自动确认。  
**成功**：录音体验保持原样。

### 场景 S6：任务重新启动

**用户**：「之前那个演讲稿做了一半，我现在想继续。」  
**VoiceOS**：如果能从可信任务记录找回目标和进度，则先展示「已知到哪一步」和下一步；若无法唯一定位，只问一个澄清问题。  
**成功**：不虚构不存在的进度。

### 场景 S7：信息不足，但要求马上行动

**用户**：「别问了，先给我一版能复制给 Codex 的提示词。」  
**VoiceOS**：明确列出假设/待确认项，生成可用草稿，并要求执行 Agent 在实地确认资料和代码环境。  
**成功**：避免以追问阻断启动，也避免装作已知事实。

## 8. 功能拆解与优先级

### P0：首个可用垂直闭环（必须实现）

| 编号 | 功能 | 可验证的行为 |
|---|---|---|
| F-01 | 入口复用 | 通过已有语音转写后的文本，以及文本入口调用同一能力 |
| F-02 | 意图识别 | 区分任务启动、普通问答、纯记录/情绪表达；尊重「不要转任务」 |
| F-03 | 路线选择 | 支持 `agent_handoff`、`guided_start`、`clarify`、`capture_only`，用户可以更改建议路线 |
| F-04 | 轻量澄清 | B 模式最多先问一个关键问题；信息不足时可带假设产出草稿 |
| F-05 | Agent 提示词生成 | 输出完整、独立、可复制的任务提示词；事实和假设分离 |
| F-06 | 操作教程生成 | 给出第一步、可执行步骤及验证方法 |
| F-07 | 预览/复制 | 沿用既有 UI/交互，能看完整交接内容并复制；如现有支持编辑则接入编辑 |
| F-08 | 状态和确认 | 草稿与确认分离；不会因复制就标记任务完成 |
| F-09 | 双模式适配 | 安静模式无打断和强制任务化，主动模式能简短澄清 |
| F-10 | 基础自动化测试 | 关键正反例、模式、权限、产物结构有自动验证或稳定测试 |

### P1：在 P0 验证后增量实现

| 编号 | 功能 | 说明 |
|---|---|---|
| F-11 | 任务恢复 | 在可信任务存储基础上找回并继续某个任务 |
| F-12 | 复用已授权上下文 | 引用短期历史、项目资料、个人知识并显示来源；敏感内容有保护 |
| F-13 | 执行器模板 | Codex / Claude Code / 通用 Agent 的适配模板，避免硬编码在业务逻辑 |
| F-14 | 学习/交付偏好 | `quick_delivery` 与 `learn_while_doing` 可切换 |
| F-15 | 人工回流 | 用户告知执行结果，更新任务状态、生成下一阶段交接 |
| F-16 | 便捷导出 | 视已有基础增加 Markdown/文件导出，而非强制重新开发导出系统 |

### 不在当前范围

- 自动远程调起 Codex/Claude Code 或任何未授权外部 Agent；
- 自主操作电脑、自动提交代码、自动发布视频或发送邮件；
- 新建复杂流程编排平台、通用 Agent 市场；
- 大规模改写 VoiceOS 的双模式/记忆/待办架构；
- 在没有可靠来源的情况下“推断”用户已经完成哪些任务。

## 9. 技术落地原则（实现由仓库现状决定）

### 9.1 先审计，不预设技术栈

开发 Agent 必须先检查：

1. 语音转写→消息→模型→回复的既有管线；
2. A/B 模式的实现与模式切换；
3. 当前知识、记忆、行动/提醒系统的实体模型与写入确认规则；
4. 是否存在已有的结构化输出、工具调用、Prompt Template、Skill、Hook 或测试框架；
5. 文件/密钥/企业资料的权限与隐私处理机制；
6. 当前代码中哪一层是最小且正确的集成点。

不得因为这份规格提出了 Task Package，就不经检查新增重复数据库、全新框架或一整套 Agent 基础设施。

### 9.2 推荐的逻辑分层（仅供映射）

```text
现有语音/文本入口
    ↓
意图与路线判断（保守）
    ↓
已授权上下文组织 + 必要澄清
    ↓
启动产物生成器
    ├── Agent 交接提示词
    ├── 自我操作教程
    ├── 澄清响应
    └── 仅记录
    ↓
现有会话 UI：预览/复制/确认
    ↓
现有任务系统：可选的持久化与后续状态回流
```

实现可以共享已有 LLM 调用与任务处理服务，不要求建立同名模块。调用结构化模型时需校验输出；解析失败要可降级为普通回复，不得产生副作用。

### 9.3 安全边界

- 内容生成与执行是两件事。首版生成指令并不授权发送到外部平台。
- 未经用户明确确认，不创建外部提醒、不可覆盖文件、不持久化为已确认的长期知识。
- 禁止在任务交接包中无提示地嵌入密钥、私人信息或公司受限内容。
- 不确定是否能访问仓库、文件、账号时，如实说明，交给执行端实地核验。
- 当用户明确要求「只记录/别处理」时，优先遵守。
- 保留错误处理路径，不让识别失败阻断正常语音聊天或录音整理。

## 11. 开发顺序与交付标准

### 阶段 0：仓库审计（必须先做）

交付简短的架构映射、复用点、需要改动的文件/接口、测试与回滚方案。需要识别哪些需求已经存在，避免重复造轮子。

### 阶段 1：P0 最小端到端闭环

先走通：**自然语言输入 → 路线判断 → 必要澄清/显式假设 → 提示词或教程 → 预览/复制 → 确认语义正确**。优先复用原有数据模型和视图。完成 T01–T13 的相关验证。

### 阶段 2：P1 任务延续

在稳定 P0 基础上，根据现有任务和记忆实现能力接入任务恢复、偏好模板、执行结果回流。不要为实现 P1 阻碍 P0 上线。

### 完成定义（Definition of Done）

1. P0 功能真实运行，不只有设计文档或假的前端按钮。
2. A/B 双模式行为符合预期，未破坏 VoiceOS 既有链路。
3. Prompt 可以脱离当前会话发送给执行 Agent，且明确事实/假设/未知信息。
4. 用户有清晰的查看、复制和确认/不保存机制。
5. 不未经授权触发外部执行或长期状态写入。
6. 关键测试通过；无法验证的项目明确说明原因和手工步骤。
7. 交付变更文件列表、使用方式、测试证据、局限与后续改进建议。

## 12. 给开发 Agent 的重要说明

本规格描述的是**用户可观察的能力**，不是要求一字不差照搬某个技术架构。请优先遵守仓库中现有的产品定义、测试规范、状态管理、能力权限和代码风格。如果规格与真实实现存在冲突，请在实施报告中解释冲突，选择最小、可回滚、可测试的兼容方案；无法确定且涉及不可逆操作时，应停止该操作并提出具体问题。

**最重要的防偏航约束：不要把 VoiceOS 做成执行型 Agent；先把用户模糊表达变成「可开始的任务」，就是这个功能首版的成功。**

# 发给 Codex / Claude Code 的 VoiceOS 开发任务提示词

> 使用说明：将本文件与 `VoiceOS_Task_Initiation_Feature_Spec.md` 放进 VoiceOS 仓库内便于 Agent 访问的位置（例如 `docs/feature-plans/`）。启动工作时把以下正文直接发给 Codex / Claude Code。若文件路径不同，请把提示词中的路径替换成实际路径。  
> 本提示词要求**审计后直接实现**，不只是生成另一份计划。

---

你现在是 VoiceOS 仓库的开发 Agent。请为这个**现有项目**实现「任务启动（Task Initiation）」功能。

## 1. 任务来源与产品定位

请完整阅读 `docs/feature-plans/VoiceOS_Task_Initiation_Feature_Spec.md`（若实际位置不同，先定位文件）。它是本次功能的需求与验收基线。

核心定位：
- VoiceOS 是用户的**语音优先、持续性的个人任务启动与协调入口**；
- Codex、Claude Code 等才是具体任务的执行者；
- VoiceOS 负责把用户自然口述中的模糊任务、障碍、想法，转译成可行动的下一步：**可复制给 Agent 的高质量提示词、供用户自助操作的教程、澄清对话或仅记录**；
- 用户可以按任务选择「快速交付」或「边做边学」；
- **不要把 VoiceOS 改造成一个新的通用执行 Agent，也不要重新实现 Codex/Claude Code 的能力。**

## 2. 请先审计真实仓库

在修改代码前，主动检查并简要汇报：
1. 仓库入口、技术栈、目录结构和当前可运行/可测试的方式；
2. 语音转写、对话状态、模型调用、UI 产物呈现的位置；
3. 原有 A「安静记录者」与 B「对话式伙伴」的实现；
4. 当前任务/提醒、短期上下文、长期知识及其确认机制；
5. 已有 prompt 模板、Skill、Hook、MCP、结构化输出、导出和测试能力；
6. 最适合复用的集成点，最小文件改动范围，以及可能发生的架构冲突。

**必须基于实际代码得出结论。**不要凭产品规格想象仓库已经有的模块，也不要为了“架构漂亮”而重写项目。

## 3. 实施策略

先给出一份简洁的仓库适配实施计划（功能切片、预计修改点、测试方式和风险），**然后在本次任务中继续实现 P0，不能停留在分析或让用户重新写需求**。如果遇到真正无法安全解决的关键阻塞，再明确指出。对于非阻塞不确定性，采用保守假设并继续。

按最小垂直切片实现：

1. 复用现有语音转写后的文本入口与文本聊天入口；
2. 识别是否需要任务启动，避免把吐槽、自由思考和「只记录」误判为任务；
3. 设计可切换的四条路线：`agent_handoff`、`guided_start`、`clarify`、`capture_only`；
4. 根据模式控制主动性：A 不打断、不强制任务化；B 可以一次问最关键的问题；
5. 交接路线生成可独立使用的任务提示词，包含目标、背景、约束、需检查的未知信息、交付物和验收标准；
6. 教程路线输出用户能真正动手的步骤与验证方式；
7. 利用现有 UI 实现预览/复制，尽量复用已有确认与存储逻辑；
8. 正确区分「草稿/已确认/已复制」与「任务已执行/已完成」；
9. 添加测试，并在有条件时实际跑通语音/转写输入到产物的流程。

先完成 P0；P1（任务恢复、模板偏好、反馈回流等）仅在原架构支持且不影响稳定交付时增加，否则列为明确后续事项。

## 4. 关键约束（不可偏离）

- **VoiceOS 是任务启动者，不是任务执行者**：V1 不自动启动 Codex/Claude Code，不自行批量改文件、不自动发布或发送内容。
- **保护用户控制权**：创建持久任务、长期认知写入、向第三方提供敏感信息等遵循现有确认/权限规则，不能由意图识别自动触发。
- **尊重双模式**：A 模式默认安静，不打断口述；B 模式可以互动，但应简洁。
- **事实与假设分开**：没有实际读取代码、文件、日程、历史状态，就绝不编造已读取或已完成。
- **不重造基础设施**：优先使用仓库已有 Skill、Hook、模型客户端、任务实体、测试工具；能复用就复用。
- **保证现有功能不回归**：任何模型结构化输出失败、识别失败，不能破坏普通聊天、录音与知识整理。
- **避免过度设计**：本期目标是可用闭环，不要求全自动编排平台、复杂多 Agent 系统或重做前端。

## 5. 质量与测试

请以需求文档第 10 节 T01–T15 为测试基线，至少实现并验证 P0 对应测试：
- 真正需要委托时生成可复制、结构完整的提示词；
- 用户希望自己学时，提供能操作的教程；
- 纯吐槽、仅记录不自动生成任务；
- A/B 模式的交互边界正确；
- 信息缺失时能澄清或标注假设，不凭空补全事实；
- 复制交接包不会误报执行完成；
- 遇到结构化输出失败可降级；
- 涉及用户数据和授权时不会无声地触发外部操作。

测试应符合仓库现有风格。运行相关测试、静态检查与构建；明确记录实际通过了什么、未能运行什么，不能把未运行测试描述为通过。

## 6. 最终交付格式

实现完成后，用中文汇报：

1. **仓库现状与集成方式**：实际复用了哪些现有模块；
2. **实现功能**：逐条对应规格中的 P0 功能编号；
3. **代码变更**：重要修改文件/接口及设计理由；
4. **使用演示**：给出至少三个例子——交给 Codex 的开发提示词、自己操作的教程、只吐槽不建任务；
5. **测试结果**：实际执行的命令与结果，哪些还需人工测试；
6. **限制与风险**：未实现的 P1、已知问题、需要用户决策的点；
7. **如何验收**：用户现在应该从 VoiceOS 哪个入口，按什么步骤测试。

**不要只写另一份需求文档或实施计划。你的工作是基于现有仓库完成可用的 P0 功能、测试和交付。**

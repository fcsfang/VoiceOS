# VoiceOS 重构原则

## 核心准则

**唯一指导原则**: [产品愿景文档](VoiceOS：产品愿景与概念设计文档%20v1.1/VoiceOS_产品愿景与概念设计文档_v1.1.md)

> **一句话愿景**  
> 让人能够毫无负担地表达，让有价值的思想被忠实理解、长期记住、恰当唤起，并与现实行动形成持续循环。

**核心价值的五个连续动作**：
1. 捕获表达
2. 理解与归属
3. 形成知识和行动
4. 跟踪后续变化
5. 在适当时机反馈

所有技术决策必须服务于这个愿景，而不是被现有代码的惯性所牵引。

## 我犯的错误（2026-10-13）

### 错误示例：4000字符限制

**我做了什么**:
- 发现 6935 字符触发了分段处理
- 查看代码，看到 4000 字符限制
- 机械地将 4000 改成 40000
- 顺着现有的 `scalarBudget` 机制走

**我应该做什么**:
1. **质疑限制的必要性**: 
   - 为什么要有字符限制？
   - 现代 LLM（GPT-6, Claude Opus 5）上下文窗口是多少？
   - 分段处理真的必要吗？

2. **从愿景出发重新设计**:
   - 愿景是什么？快速理解语音内容
   - 限制是否阻碍愿景？是的，强制分段增加延迟和复杂度
   - 正确做法是什么？移除不必要的限制，让 LLM 能力决定边界

3. **可能的更好方案**:
   - 完全移除硬编码的字符限制
   - 根据实际 API 的 token 限制动态决策
   - 或者直接查询模型的上下文窗口，而不是猜测一个数字

## 正确的思维模式

### ❌ 错误的惯性思维

```
看到代码 → 理解逻辑 → 跟着逻辑走 → 微调参数
```

这是**维护者思维**，会永久继承历史包袱。

### ✅ 正确的重构思维

```
遇到问题 → 回到愿景 → 质疑现状 → 重新设计 → 验证对齐
```

这是**设计者思维**，会主动优化系统。

## 具体指导原则

### 1. 先问"为什么"，再问"怎么做"

遇到任何代码逻辑：
- ❌ "这里限制了 4000 字符，我改成 40000"
- ✅ "为什么要限制字符？这个限制在 2026 年还合理吗？"

### 2. 用现代技术能力重新评估

技术在进步：
- 2021: GPT-3 (4K tokens)
- 2023: GPT-4 (128K tokens)  
- 2024: GPT-4 Turbo (128K tokens)
- 2025: GPT-5 (1M+ tokens)
- 2026: GPT-6 (更大的上下文窗口)
- Claude: Opus 5 支持 200K tokens

代码不能停留在 2021。

### 3. 删除而非绕过

发现不合理的地方：
- ❌ 添加配置项、特殊处理、兼容逻辑
- ✅ 直接删除不合理的部分

### 4. 从愿景验证每个决策

每次修改前问自己：
1. 这个改动让愿景更近还是更远？
2. 这个改动是解决问题还是绕过问题？
3. 如果我从零开始设计，会做这个选择吗？

## 我需要改正的地方

### 技术信息更新

- ❌ "GPT-4 supports 128K tokens"  
- ✅ "GPT-6 和 Claude Opus 5 的上下文窗口是多少？我应该查询最新的模型能力"

我引用的模型信息已经过时。作为 2026 年的系统，应该基于当前最强模型的能力设计：

**2026 年的 LLM 现状**：
- GPT-6（最新）：上下文窗口和能力未知，需要查询
- GPT-5：1M+ tokens
- Claude Opus 5：200K+ tokens
- 多模态能力：原生支持音频、图像、视频

分段处理在 2021 年可能是必需的（GPT-3 仅 4K tokens），但在 2026 年已经完全不必要。

### 主动思考深度

我应该：
- 质疑每一个看到的限制
- 查询最新的 API 能力边界
- 从愿景倒推应该的设计
- 而不是从现有代码正向推演

## 后续工作方式

在推进重构之前，我需要先建立正确的思维框架：

### 1. 深度理解愿景

✅ 已阅读产品愿景文档核心部分：
- **核心使命**：降低表达成本、忠实形成知识、连接思想与行动、延续认知过程、保护注意力
- **五个连续动作**：捕获表达 → 理解与归属 → 形成知识和行动 → 跟踪后续变化 → 在适当时机反馈
- **关键边界**：用户思想优先、原始依据可回溯、无负担使用、自主权有边界、演进时数据不断裂

### 2. 从愿景审视现有代码

每遇到一个模块，先问：
- **这个模块在五个连续动作中的位置是什么？**
- **它是否真正服务于愿景，还是历史包袱？**
- **如果从零开始设计来实现这个愿景，我会这样做吗？**

### 3. 查询 2026 年的技术边界

需要确认的技术现状：
- [ ] GPT-6 的上下文窗口和能力
- [ ] Claude Opus 5 的实际限制
- [ ] Whisper v3/v4 的转写质量
- [ ] 是否有原生音频输入的 LLM（不需要先转文字）
- [ ] 本地 LLM 的实际可用性（Mac M4 上的性能）

### 4. 识别需要质疑的部分

基于愿景和 2026 年技术现实，我怀疑这些可能是过度设计或历史包袱：

#### 高度怀疑（可能完全不需要）
- **分段处理的整个系统**：如果 GPT-6 支持百万级 token，为什么要切段？
- **4000/40000 字符限制**：这个数字本身是否还有意义？
- **复杂的状态机**：是否有些状态转换是防御性的、实际不会发生的？

#### 需要深入分析
- **本地 vs 云端的权限控制**：愿景文档提到"充分相关上下文优先于极端数据最小化"，现有实现是否过度复杂？
- **多层确认机制**：snapshot、validation、fingerprint、digest——这些是必需的安全边界还是过度工程？
- **录制处理请求的等待状态**：用户录音后等待转写，这符合"无负担使用"吗？

### 5. 重构优先级

从愿景的五个阶段倒推：

**阶段1：捕获表达**
- 当前：录音 → 保存 → 转写
- 质疑：转写必须异步吗？本地实时转写可行吗？

**阶段2：理解与归属**  
- 当前：调用 GPT 理解文本
- 质疑：如果 LLM 支持原生音频输入，是否可以跳过转写？

**阶段3：形成知识和行动**
- 当前：复杂的多层知识系统和行动系统
- 质疑：MVP 真的需要这么复杂吗？先跑通闭环更重要

**阶段4：跟踪后续变化**
- 当前：关联、版本、修正机制
- 质疑：首版需要多完善？

**阶段5：适当时机反馈**
- 当前：主动反馈系统
- 质疑：这部分是否已实现？如果没有，前面的复杂度是否本末倒置？

### 6. 下一步行动

在继续修改代码之前：

1. **查询 2026 年 LLM 能力**（WebSearch）
2. **审视整体架构**：哪些模块是必需的，哪些是过度设计
3. **识别最小可行路径**：愿景文档说"首版必须从表达走到知识、任务、后续行为和认知更新"，当前代码距离这个目标有多远？
4. **大胆删除**：移除不符合愿景或技术现实的部分

我不再是维护者，我是重构者。目标不是让现有代码跑起来，而是让它符合 2026 年的技术现实和产品愿景。

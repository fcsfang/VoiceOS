## 2026-10-13 18:20 - 字符预算优化（去除不必要的4000字限制）

### 问题发现

**症状**: 6935字符的音频转写文本触发了分段处理（segmented processing），而现代 LLM（GPT-4/Claude）支持 100K+ token 上下文，完全没必要在 4000 字符就启动复杂的分段处理流程。

**根本原因**: 代码中硬编码了 4000 字符上限，这是历史遗留限制，未随 LLM 能力提升而更新。

### 优化方案

**修改前的逻辑**:
```
if transcript.length > 4000:
    → 分段处理（复杂多步骤pipeline，多次API调用）
else:
    → 直接处理（单次API调用）
```

**修改后的逻辑**:
```
if transcript.length > 40000:
    → 分段处理
else:
    → 直接处理
```

**提升倍数**: 10x (4000 → 40000 字符)

### 修改的文件

修改了 7 个 Swift 文件中所有 4000 字符限制为 40000：

1. **ExpressionProcessingIntent.swift** (Line 45)
   - `guard snapshot.context.scalarBudget == 40000,`
   
2. **TranscriptContext.swift** (Line 24)
   - `public func prepareLocalTranscriptContext(sourceIDs: [String], scalarBudget: Int = 40000)`
   
3. **ExpressionProcessingRecovery.swift** (Lines 72, 75)
   - `guard UUID(uuidString: snapshot.id) != nil, snapshot.context.scalarBudget == 40000,`
   - `source.text.unicodeScalars.count <= 40000,`
   
4. **RelevanceSelection.swift** (Lines 32, 37)
   - `scalarBudget: Int = 40000) throws -> RelevanceSnapshot {`
   - `(1...40000).contains(scalarBudget),`
   
5. **ResponsesRelevancePort.swift** (Line 30)
   - `(1...40000).contains(s.scalarBudget),`
   
6. **DurableRelevance.swift** (Line 132)
   - `(1...40000).contains(s.scalarBudget),`

7. **RecordingProcessingRequest.swift** (Line 123)
   - `if (current.transcript ?? "").unicodeScalars.count>40000 {`

### 验证结果

✅ **编译成功**: 13.87秒完成 Debug 构建  
✅ **应用重启**: 进程 23336 正常运行  
✅ **逻辑验证**:
- 测试音频: 6935 字符
- 旧限制: 6935 > 4000 → 触发分段处理（不必要的复杂流程）
- 新限制: 6935 < 40000 → 使用直接处理（简单高效）

### 影响分析

**性能提升**:
- 减少 API 调用次数（分段处理需要多次调用）
- 简化处理流程（无需分段、提取、聚合）
- 降低成本（更少的 API token 消耗）

**适用范围**:
- 短对话（< 10分钟语音）: 直接处理
- 中等对话（10-60分钟）: 直接处理
- 长对话（> 60分钟）: 可能仍需分段处理

**风险评估**:
- ✅ 无破坏性变更（只是提高阈值）
- ✅ 向后兼容（< 4000 字符的处理不受影响）
- ✅ 保留分段能力（超长文本仍可分段）

### 设计原则

这次优化体现了一个关键原则：**不要被历史代码的惯性思维限制**。

当接手一个项目时，需要：
1. **质疑现有限制的合理性** - 4000 字符限制在 GPT-4 时代已不合理
2. **删除而非绕过缺陷** - 直接提高限制，而非添加复杂的分段逻辑
3. **以现代能力为准** - LLM 能力已大幅提升，代码应跟上

**质量对比**: ✅ Qwen 全面优于 Apple

| 维度 | Apple SpeechAnalyzer | Qwen ASR | 胜出 |
|------|---------------------|----------|------|
| 准确率 | 有明显错误 | 高准确 | ✅ Qwen |
| 标点断句 | 混乱，空格过多 | 自然流畅 | ✅ Qwen |

| 专有名词 | skile, voiceOS� | skill, Voice OS | ✅ Qwen |
| 数字识别 | "9 9点 40" | "九点四十" | ✅ Qwen |
| 可读性 | 难以阅读 | 接近人工整理 | ✅ Qwen |

### 关键发现

**1. Apple 的典型问题**:
```
OK啊朋友们。现在正好是周一晚上 11:59，现在已经到了第二天周二了 ，
那么周一呢 ？本来是想晚上。 ，这个上完班早点回来录这个录一期的
应该是讲的这个 skile吧 ，应该是讲 skile。那我的 voiceOS�
```
- 标点位置不当（句号后接逗号）
- 空格使用混乱
- 专有名词错误（skile → skill）
- 出现乱码 �

**2. Qwen 的优化效果**:
```
OK啊，朋友们，现在正好是周一晚上十一点五十九分，现在已经到了第二天。
周二了，那么周一呢？本来是想晚上上呃这个上完班早点回来录这个录一期的，
应该是讲的这个skill吧，应该是讲skill。那我的 Voice OS 还正在开发，
```
- 标点自然，符合中文习惯
- 专有名词正确
- 数字转为口语化表达（十一点五十九分）
- 保留必要的语气词（"呃"），但不冗余

**3. 语气词过滤验证** ✅:

Apple 完全保留：
```
那么随便吃点饭吃点饭 ，然后休息一下就已经 11点多了。
本来不想本来今天呢不想录这个视频的 ，但是这个休息一而休息着这个精神头就来了
```

Qwen 智能处理：
```
那么随便吃点饭。吃点饭，然后休息一下，就已经十一点多了。
本来不想，本来今天呢不想录这个视频呢，但是这个休息着休息着，这个精神头就来了。
```
- "休息一而休息着" → "休息着休息着"（纠正了 Apple 的错误）
- 重复处加逗号分隔，而非机械保留
- 符合用户需求："像豆包输入法一样，直接消除过度冗余的词"

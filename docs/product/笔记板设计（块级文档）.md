# 笔记板设计：把待办、想法、观点都承载到笔记上（v0.1 提案，待确认后实施）

> 用户判断：笔记这条路效果不错；但首页以材料为单位、材料页以「观点/要点」组织，都不如笔记。问题是笔记怎么组织——能不能把待办、想法、观点都承载到一块「笔记板」上？板内承载形式要多样，不仅是可视化多样，组件也要多样。这是一个重要的产品转向。

## 1. 核心判断

1. **板 = 块级文档。** 笔记从「一篇带批注的文章」升级为「一块由组件构成的板」：文字块仍是骨架，待办块、观点块、引文块、AI 批注块、材料块等组件插在其中，纵向阅读。延续 203 的原则：kind 是自由字符串，渲染层按已知块渲染、未知块降级为文本摘要；新增组件只改渲染层与提示词。
2. **引用而非复制。** 待办块引用 actionID、观点块引用 claimID、引文块引用 spanID。板上渲染的是实时状态：待办勾选、观点变化、任务完成在板上即刻反映，不产生第二份事实。模型只决定「放什么、放哪里、怎么标注」，不复制数据。
3. **板是成品，材料退为来源。** 每行首页 = 一块板；材料不再是组织单位，只是板的来源与「查看材料与原文」的去处。没有笔记的材料第一次打开时懒生成一块板。
4. **模型自由。** 块的选择、顺序、重点标记、批注、角色全部由模型判断，不设条数与形式上限；我们只定义承载（块协议、渲染能力、输出预算）与诚实（引用 id 必须来自输入；不虚构用户事实）。

## 2. 块模型（草案）

```swift
struct NoteBoard: Codable {
    let title: String
    let lead: String?
    let blocks: [NoteBlock]
}
struct NoteBlock: Codable {
    let id: String          // 渲染锚点与阅读位置用
    let kind: String        // 自由：text/todo/claim/quote/insight/callout/materials/…
    // 各 kind 的可选载荷（schema 中全部列出、required 仅 kind+id）
    let text: String?        // 文本块正文（含 marks/annotations 旧结构）
    let heading: String?
    let paragraphs: [MaterialNote.Paragraph]?   // 文本块复用现有段落（marks/annotations）
    let actionID: String?    // todo：引用行动
    let claimID: String?     // claim：引用观点
    let sourceID: String?    // quote/materials：来源
    let spanID: String?
    let quote: String?
    let titleOverride: String?
    let tone: String?
    let annotation: MaterialNote.Annotation?    // insight 块
}
```

- 兼容：旧笔记 {title, lead, sections, closing} 经适配器转为 text 块（每节一块）；新笔记从提示词 v6 起产出 blocks；旧版本照常可读。
- 搜索/预览：取 title、lead 与首个 text 块；阅读位置锚点改用块 id（块 id 由生成端给出，重生成时位置失效则从顶部）。
- 未知块：渲染为「来自 AI 的 {kind}」轻卡片并展示其文本；不丢内容、不报错。

## 3. 生成（material-note-v6，同一次调用）

- 输入在现有 members 之外加入：当前表达的 actions（id/标题/状态/期限）、claims（id/陈述/认可状态）与相关讨论成果；这是一份 id 快照，模型只能引用、不能发明。
- 模型输出 blocks：决定哪些待办与观点值得上板、插在哪一段之后、要不要标注或加批注；文字块承载原意与叙述；长批注可作为 insight 块独立成段，短批注仍可就地内联（两种都允许，由模型选择）。
- 引用校验：保存前逐个把 actionID/claimID/sourceID 解析到现有记录；解析失败的块降级为纯文本块（保留模型写的文字），不整篇丢弃。
- 输出预算保持 32768 并按需再提；reasoning effort high。

## 4. 交互（分阶段）

- P3 第一版：块级只读 + 有限操作——待办块勾选写回行动状态、观点块打开原话/讨论、引文块展开原文、材料块跳「查看材料与原文」、批注块可收起；不做自由编辑与拖拽排序。
- 后续按需要再放开编辑（编辑文字、移动块）——板以引用为主，文字编辑不影响引用块。

## 5. 首页与材料页的收敛

- 首页：每行一块板（已有笔记标题/预览）；无笔记材料首次打开懒生成板。
- 材料页：板成为主视图；「要点/待办」等重复区块从材料页移除（板已承载），材料页只保留页头与原文侧；材料列表退为来源管理。
- 主题页不变（关切层），板与主题通过观点引用自然相连。

## 6. 风险与对策

- **生成成本上升**：blocks 决策 + 引用快照 → 输出预算提升；同一次调用完成，不新增往返。
- **实时引用 vs 历史版本**：板上待办/观点显示当前状态；打开历史版本时提示「组件为当前状态」。这是选择引用而非复制的代价，换来没有第二事实源。
- **组件滥用**：可能出现每段都挂待办；靠目标句与批注质量门槛约束，不设数量上限。
- **未知块降级**：保证不丢内容、可读。

## 7. 分阶段

- P1 数据与渲染：NoteBoard/NoteBlock 模型、旧笔记适配器、BoardView（text/todo/claim/quote/insight/callout/materials），旧文章路径保留为兼容分支。测试：适配器、未知块降级、块锚点。
- P2 生成：提示词 v6 + 引用快照 + 校验降级 + 保存/预览/搜索接线。测试：引用校验、降级。
- P3 交互与收敛：勾选写回、跳转；首页/材料入口切到板；材料页移除重复区块；上机验收。
- P4 打磨：手账样式、长板懒加载、历史版本提示。

## 8. 待确认

1. 板的操作深度：第一版只读+勾选/跳转，还是允许编辑文字与拖动排序？
2. 待办/观点上板策略：模型按相关性自由选择，还是全部上板？
3. 材料在板上：保留一个「来源」块，还是完全隐去（只留「查看材料与原文」）？
4. 旧笔记：保持旧版原样按文章阅读，还是给一个「一键全部重生成成板」的入口？

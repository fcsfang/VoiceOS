# 录制并处理：转写前的持久请求

日期：2026-10-12。承接[个人录音逐字稿持久链](m4-personal-audio-processing.md)。

## 需求与边界

用户选择“录制并处理文字”后，即使应用在录音、封存、转写或队列交接时退出，这次明确的处理请求也必须可追溯。普通录制仍只本地保存和转写；模式 B 的逐轮录音也保持原流程，不自动提交讨论或创建模式 A 的请求。此入口允许处理本次表达的文字，原始音频不上传。

## 实现契约

`recording_processing_requests` 保存请求命令、来源及原件版本、初始授权版本、认知/关联端口身份、后续队列身份、状态和错误。无 API key，无原始音频载荷。

开始设备采集前，在同一数据库事务中保存录音来源、文本授权历史和请求。云端目的地仅对这一新来源记录 local_only=0、policy_version=2；本地目的地维持默认版本1。不能重放普通录制命令来升级处理范围，也不能用同一命令切换模型。

| 请求状态 | 含义和允许操作 |
|---|---|
| waiting | 等待封存及本地转写；可取消文字处理，录音/转写保留 |
| enqueued | 已移交原持久处理队列；查看该队列的实时/终态回执及取消入口 |
| blocked | 身份、授权、模型、更正或预算不符；不自动恢复发送 |
| cancelled | 用户取消处理；保留本地来源和历史 |
| frozen | 迁移后冻结；不自动派发 |

转写失败保持 waiting，用户明确重试本地转写后再核对；未封存录音必须明确核对封存，启动恢复不会把片段自动认定为完整表达。来源/政策变更、端口身份变化、已更正逐字稿、空逐字稿及超过4000字符预算均阻断自动移交，完整原件和文字仍保留。

完成转写后创建既有 processing_intents，使用 `record-process:<requestID>` 稳定命令。队列提交与请求更新是两个短事务；若中间退出，恢复核对命令、来源、授权和端口身份，找回同一队列，不创建第二条。这个窗口的取消也会查找已提交队列并取消；已完成/未知/冻结等终态不会被误报为已取消。

请求本身不发模型请求。控制中心先跑本地转写、核对等待请求，再启动原队列执行器；退出恢复、认知/关联回执及 unknown 不重发全部复用原实现。

## 迁移与取舍

数据库升级到 schema26。含录制处理请求的导出包为 v26/schema26，包含请求表；没有请求时继续使用原范围的 v24或v25/schema25，避免向旧客户端输出它不能解释的新表。恢复支持旧包，v26 中请求和执行队列均冻结。把携带请求表的包改成旧版本会被拒绝；授权和队列关联在恢复时再次校验。

详见[ADR024](../adr/024-recording-processing-request.md)。选择独立请求表，避免把尚无逐字稿的对象塞进不可变队列快照，也避免使用会随退出丢失的内存标记。

## 验证

- 376项测试通过，包括11项新增请求测试；覆盖原子回滚、普通保存边界、重启未封存录音、独立授权、模型变化、失败后显式转写重试、更正阻断、超预算、交接窗口恢复/取消、已完成队列取消及迁移冻结。
- [实际强退证据](../research/evidence/recording-processing-recovery-2026-10-12.json)：七个 SIGKILL 窗口，每个验证重复恢复及重复续接的稳定身份/调用数量。录音请求未提交回滚；已提交但未采集保持 waiting；转写已提交或队列交接后安全续接；认知已 reserved 则 unknown、不重发。
- 签名构建、严格签名校验通过；原生界面验证了分开的录制入口、未配置模型时处理入口禁用、重启后 waiting 可见、取消后状态持久为 cancelled，队列及模型调用仍为0。

本轮使用明确标记的合成音频和逐字稿，没有开启麦克风、上传音频、调用云端模型或写提醒事项。尚未完成“真实设备录制并处理”及自然语义质量/真实行动反馈的完整验收。之前的真实播客转写证据仍成立，但不替代这些缺口。

## 接续

先复核自然逐字稿更正与来源引用的有效性，并完善长录音的预算呈现和分段方案；再用有限真实语义样本验收候选、行动及反馈。长录音不得静默截断，已确定的观点与任务归属边界不能为扩大处理范围而改变。

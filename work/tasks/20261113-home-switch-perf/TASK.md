# 首页材料切换卡顿

## 目标

用户报告在首页点击不同材料来回切换时很慢、不跟手。目标：把点击到渲染之间的计算成本降下来，用实测数字证明。

## 基线（实时库副本，78 份材料、1051 条观点、54 个首页条目）

- 每次首页渲染重建整份「最近」索引 6.0 毫秒。
- 时间线 54 行每行重建摘要合计 449.1 毫秒（debug，中位数 5 次），单条最大 177.8 毫秒；选中材料的正文摘要再建一次。
- 根因在 `RecentContentDigest.ranked`：排序比较器里对左右两侧都重算 `leadScore`，每次比较扫描 26 个反思词 + 13 个具体词的全部出现次数，n=112 时约 1500 次评分。

## 修复（两轮，各自可验证）

- 第一轮（`c214978`）：评分先算一次再排序，复杂度从 O(n log n × L × W) 降到 O(n × L × W)。同一副本实测：每渲染摘要 449.1 → 79.7 毫秒（debug），release 77.8 毫秒。
- 第二轮（`7e308cd`）：新增 `RecentContentHomeSnapshot`，在工作区刷新末尾一次性算出「最近」索引与每行摘要（含任务过滤），首页渲染只读缓存。`reloadWorkspace` 是唯一同时写 records/claims/actionRecords 的位置，缓存不会陈旧。

## 修复后数字（同一副本）

- 快照构建：98.5 毫秒，每次工作区刷新一次。
- 渲染路径（54 项摘要查表，模拟 200 次）：每次 17.1 微秒。
- 点击到渲染前的摘要计算从 449.1 毫秒降到约 0.02 毫秒。

## 验证

- `swift build -j 4` 通过；`swift test -j 4` 119 项 0 失败（新增快照等价测试：与直接调用索引构建和逐条摘要构建结果一致，含任务过滤）。
- 测量在同一条目、同一份实时库副本上完成；release 构建单测数字与 debug 同量级。

## 残余与未测

- 工作区刷新时主线程新增一次 98.5 毫秒的构建，属每次刷新一次而非每次点击；若日后仍觉得刷新卡顿，可把它移到后台。
- SwiftUI 布局与文本排版耗时未单独测量；真实手感需部署后在应用里确认。
- 另一条独立热点（工作区快照 29.6 秒，含 163 份跟进回执校验 8.6 秒）不在本次范围。

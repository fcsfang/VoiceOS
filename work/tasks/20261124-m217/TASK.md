# 217 内部配置后的功能断点与自动入口可见性

目标：把 216 之后「配置内部化、核对 v4」暴露出来的功能断点补上，并让自动入口在等待重试时不再看起来像什么都没发生。

## 背景

- 216 已把文本模型配置从外部文件迁到应用内部（UserDefaults + 钥匙串），核对与完整整理都走进程环境拿到型号与强度。
- 已知残留：`Sources/VoiceOSApp/BilingualView.swift` 的 `BilingualClient.init` 仍要求 `voiceos.textModelConfigPath.v1` 指向的配置文件；内部配置下「译文对照」会提示「先在设置中选择文本模型」。
- 今天 13:47 的语音备忘录三次被门控挡住后转 needsAttention，用户在界面上看不到任何提示，以为录音没有进入流程。阻塞原因虽已拆分，但「等待手动重试」本身没有可见性。

## 调查

- 三个只读发现者并行：
  1. 全仓扫描仍依赖外部配置文件或绕过内部配置的位置（Bilingual 之外还有多少）。
  2. 自动入口链路的缺口：needsAttention 可见提示、应用未运行时的文件发现、失败计数与去重键。
  3. 审查 216 提交本身（Python 与 Swift）的真实缺陷。

## 结果

三个只读发现者返回：外部配置残留 5 条、自动入口缺口 8 条、216 提交缺陷 8 条。本波取其中互相印证、影响最大的十处：

### 内部配置断点
- `BilingualClient` 改读内部配置（`TextModelConfiguration.load()` + `TextModelKeychain.apiKey()`），删除私有文件解析器；「译文对照」在内部配置下恢复可用，旧文件回退路径与写死的 `gpt-6.1-sol` 一起消失。
- 导入 JSON 配置补读 `reviewEffort`；`loadSuite(settings:)` 的报错不再把用户引向 `.env`。
- 设置页保存改为「先让端口策略接受这份配置，再写钥匙串与配置」：校验失败不再留下半保存状态，密钥不会随未通过校验的地址进入整理脚本；保存成功后清掉旧的导入文件指向。
- `textModelOrganizerEnvironment` 只在端口就绪时生成，避免把钥匙串里的密钥交给尚未通过校验的地址。

### 自动入口
- 修复 216 引入的卡死路径：清理同路径旧条目时不再删正在处理的条目；`finish` 无论条目是否存在都释放 `activeFolderID`。
- 新增 `.deferred` 结果：等待配置、另一段整理占用、应用退出中断都不再消耗三次自动重试预算，也不会在六分钟内被烧成 `needsAttention`。
- 转 `needsAttention` 时发系统通知，状态行写明文件名与原因；侧栏「需要查看」计入录音条数；处理情况页列出每份待处理录音的原因。
- 失败分类改为结构化：HTTP 408/429/5xx 与转写未完成算瞬时；401/403 明确提示检查密钥与权限；取消与中断不再计次。
- 扫描被门控挡住时，状态行显示「发现 N 份新录音，等待处理条件」。
- 启动时书签过期会重新生成并保存。

### 笔记批量
- 批量整理前核对该笔记的全部成员（本人录音 + 配对节目轨），不再只核对被选中的本人材料。

### Python（216 提交审查）
- `settings()` 改为按字段合并环境与文件；`.env` 接受与导入器一致的别名（`OPENAI_MODEL`/`VOICEOS_TEXT_MODEL`、`OPENAI_REVIEW_EFFORT`/`VOICEOS_REVIEW_EFFORT`）。
- 缓存身份加入端点、模型与强度：`ask()` 的 `input_digest`、质量核对目录、意图候选 digest、全文校正回执目录都随设置变化，改模型后重试会真正重新请求。
- 格式修复轮加入本地合并校验：第一轮已通过校验的片段必须原样保留，修复轮改写这些条目会被拒绝。
